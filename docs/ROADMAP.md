# 分阶段开发路线

## 1. 总体依赖与阶段门

```text
P0 reliable local capture
 ├──> P1 WeRead capture adapter
 └──> P2 indexing + writing
        └──> P3 scientific-tool exchange
```

P1 和 P2 都依赖 P0 冻结的捕获/Markdown契约；二者在 P0 完成后可以分别开展，但默认按 P0 → P1 → P2 顺序降低变更成本。P3 必须依赖 P2 的来源 revision、候选审核和文章版本能力，并在开始前检查科学化工具的真实实现。

每个阶段只有在自动化验收、人工验收、文档同步和风险报告都完成后才通过阶段门。通过某阶段不授权自动开始下一阶段。

## 2. P0：Windows 本地记录基础

### 状态

P0 可靠写入核心已完成；桌面体验已按 2026-10-22 的用户反馈重构为右缘感应入口、连续笔记页和固定 `doc` 文档根。P0 当时的 23/23 自动化测试通过。多显示器/DPI、中文 IME、睡眠唤醒和右缘误触仍待用户按 `docs/P0_MANUAL_TESTS.md` 验收，因此 P0 阶段门尚未最终关闭；P1 已由用户另行明确授权并实施。

### 目标

形成不依赖 AI、可以每天实际使用的本地记录最小闭环：鼠标贴边唤起、低摩擦 Markdown 输入、可靠写入每日文件、失败可恢复且重试不重复。

### 子任务

#### P0.0 工程与技术 spike

- 已建立 .NET 10 solution、忽略规则和本地脚本；按用户约束未初始化 Git。
- Tauri 构建链因 MSVC Build Tools 安装被系统盘空间阻断，已按降级门切换到 .NET 10 WPF。
- 已实现单实例、右缘感应按钮、重复启动激活、当前屏幕右侧窗口和原生输入；多显示器/DPI、中文 IME、休眠和安装体验保留为人工验收。
- 同进程回环 HTTP API、配置端口和应用退出清理已实现并自动化验证。
- 详细证据和未验项目记录在 `docs/P0_TECHNICAL_SPIKE.md`。

#### P0.1 契约与核心领域

- 将 `CaptureRequest/Response`、错误码和 Markdown v1 标记转成 JSON Schema/OpenAPI 与契约测试。
- 实现 UUID、UTC/时区/本地日期规则、内容限制、路径规范化。
- 实现 Markdown 渲染与解析器，先以纯函数和 fixture 验证边界。
- 建立 SQLite migration、捕获账本状态机和 repository。

#### P0.2 可靠写入

- 建立模拟 Vault 和单一写入队列。
- 实现每日文件创建、追加、flush、回读 ID 验证和前后指纹。
- 实现 `request_id` 幂等、同键异载荷冲突、并发串行化和启动恢复。
- 处理文件占用、磁盘满/权限、路径移动、部分写入和重复启动。
- 提供恢复报告，任何无法确认的状态不显示“保存成功”。

#### P0.3 桌面笔记体验

- 实现右缘 6 像素感应区、悬停展开按钮、重复启动激活、右侧面板、草稿持久化和提交状态；不注册全局键盘组合、不使用托盘。
- 历史记录与当前输入在同一连续页面呈现，不显示“只读/新增”分区；每段只显示小时级元信息。
- 用户内容固定写入程序目录下 `doc`；设置只显示路径、打开文件夹和退出。
- 实现跨日提示、Markdown 输入和已保存记录解析；历史记录仍通过可靠追加协议保护，不做整页覆盖。
- 开机启动和自动 Git 快照均为显式用户选择。

#### P0.4 测试、打包与文档

- 单元、契约、SQLite migration、集成和故障注入测试。
- Windows E2E 覆盖启动/右缘唤起 → 提交 → 文件落盘 → 重试。
- 打包本地安装候选，记录签名/SmartScreen 现实限制。
- 完成用户配置、备份、故障恢复和卸载说明。

### 技术依赖

- .NET 10 WPF、ASP.NET Core、SQLite（P0 spike 已按 ADR-006 从 Tauri 降级）。
- 外部 Markdown 编辑器是可选能力，P0 不依赖 Obsidian URI 或第三方插件。
- 测试只使用临时模拟文档库。

### 交付物

- Windows 采集主机与安装/便携运行说明。
- Capture API v1、Markdown protocol v1、数据库 migration。
- 模拟 Vault、自动化测试和故障恢复测试报告。
- P0 操作手册、数据位置说明和更新后的决策/状态文档。

### 自动化验收

- 100 次相同请求重试只产生一个 `entry_id` 和一个记录块。
- 多客户端并发提交全部可回读，ID 唯一，文件可解析，无交叉破坏。
- 在“文件已写入、响应前崩溃”故障点重启后返回原结果，不重复追加。
- 跨午夜、时区更改、中文/Emoji、Markdown/HTML 注释、超长允许内容均按契约工作。
- 文件占用、只读目录、磁盘/写入模拟失败时不误报成功，恢复状态可见。
- 删除 index/临时状态不影响原始 Markdown；捕获账本一致性检查通过。
- 安全测试证明 API 不监听非回环地址，未认证与错误 Origin 请求被拒绝。

### 人工验收

- 右缘感应条、悬停按钮和重复启动在多个显示器、不同 DPI 下唤起正确。
- 中文输入法、粘贴、撤销、隐藏/恢复和草稿体验可用。
- 外部 Markdown 编辑器能正常阅读每日文件；外部编辑后再次追加不会覆盖已有内容。
- 睡眠/唤醒、重启和应用升级后配置与未提交草稿符合预期。
- 用户确认便携目录备份后，才在发布目录的 `doc` 中做一条受控真实记录验证。

### 风险与降级

- Tauri 构建链未达门槛，P0 已切换到 .NET 10 WPF；若 WPF 人工验收发现 IME/窗口问题，仅在 P0 范围内修复后复测。
- Obsidian 全文件保存与追加冲突：短期显示占用并重试；必要时引入本地 spool，明确“已接收、待写入”，不谎报落盘。
- 安装签名成本：先提供本地开发/便携构建和校验说明，不关闭系统安全功能。
- 本地 API 被策略拦截：P1 前评估 Native Messaging；P0 桌面内部仍可用。

### 独立可用性

通过验收后可以独立投入日常使用；不需要 P1/P2。它应是第一个稳定产品，而非后续 AI 功能的临时脚手架。

## 3. P1：微信读书 Chrome 插件

### 状态

P1 v0.1.2 的实现范围为 Manifest V3/Side Panel、来源适配器、Markdown 笔记、草稿来源快照、P0 配对凭证、统一写入和状态查询。真实页面选区在人工验证中不能可靠交付，用户于 2026-10-22 明确决定跳过；相关界面、代码与额外权限已移除，不再是 P1 验收项。自动化验证结果见 `docs/PROJECT_STATUS.md`；真实登录页面、Chrome 重启、实际超时和 Obsidian 展示仍待按 `docs/P1_CHROME_EXTENSION.md` 人工验收，因此 P1 阶段门尚未关闭。

### 目标

在微信读书网页版提供低摩擦侧栏，可靠提交带来源快照的 Markdown 笔记，复用 P0 的写入链路。

### 前置依赖

- P0 Capture API/Markdown v1 已冻结并有版本兼容策略（已满足）。
- Capture Host 有安全配对/令牌轮换设计（一次性码、扩展 Origin 绑定与同 ID 重配轮换已满足；独立服务端撤销 UI 未实现并已披露）。
- 用户已明确授权 P1；真实 Chrome 配置和登录页面兼容性仍需人工验收。

### 子任务

- 已建立 Manifest V3 TypeScript 扩展、最小权限清单和构建/加载说明。
- 已实现 Side Panel UI、按标签页草稿、提交状态、超时状态查询和保留同 ID 的手工重试；未增加自动后台队列。
- 已将页面识别封装为 `weread-dom-v1` 适配器，输出统一 `SourceContext`。
- 已处理 SPA 导航观察、延迟 DOM 更新、章节变化和上下文冻结；真实页面时序待验。
- 已按用户决定移除选文引用入口、右键菜单和选区读取权限；当前版本只提交用户在侧栏中输入的 Markdown。
- 已建立一次性码配对，不硬编码长期令牌；同扩展重配可轮换，扩展可删除本地凭证。
- DOM 字段缺失显示降级信息；完全不符合阅读页 URL 的页面不允许新草稿冒充微信读书来源。
- 已保存两种脱敏 HTML fixture 和适配器版本，并建立回归测试。

### 交付物

- 可开发者模式加载的扩展包和后续打包说明。
- Weread 适配器接口、fixture、选择器策略和兼容性报告。
- 配对/撤销/离线重试说明。
- 更新后的 Capture 契约和 P1 状态文档。

### 自动化验收

- fixture 覆盖有/无作者、章节、未登录、加载中和至少两种页面结构。
- SPA 章节切换后新提交使用新快照；旧草稿明确显示上下文变化并由用户选择是否更新。
- Capture Host 离线时草稿不丢；上线重试保持同一 `request_id`，不重复落盘。
- 普通网页脚本无法凭 Origin 绕过认证；扩展不拥有文件系统和不必要站点权限。
- 适配器异常不影响自由记录；来源字段缺失保持 `null`/空数组。

### 人工验收

- 在真实微信读书页面核对书名、作者、章节、书 ID 和 URL。
- 侧栏在阅读、翻页/滚动、切章和浏览器重启后的体验可接受。
- 用户知晓侧栏显示在左侧还是右侧由 Chrome 设置决定，扩展只保证侧栏能力。
- 用户能在提交前看见来源信息，并在来源变化时选择保留原绑定或改绑当前页。
- 每条记录在 Obsidian 中可读，来源与个人笔记视觉上清晰。

### 风险与降级

- DOM 频繁变化：优先稳定 URL/页面状态，再使用选择器；失败时只保留 URL + 用户输入。
- Side Panel API 兼容问题：当前基线为 Chrome 114+；必要时降级为扩展 popup 或 content-script 内可关闭面板，业务契约不变。
- localhost API 受限：切换 Native Messaging；不让扩展直接写文件。
- 网页选区读取在真实微信读书页面未达到可靠性门槛，已从 P1 v0.1.2 撤下；只有用户另行授权新范围并建立真实页面回归证据后才重新评估。

### 独立可用性

依赖 P0 Capture Host 才可用；不依赖 P2，完成后即可作为第二采集入口日常使用。

## 4. P2：Agent 自动整理与文章维护

### 状态

P2.0–P2.4 的本地最小闭环已实现：增量索引、可重建 FTS、Codex workset/submission 协议、主题与文章提案、基线冲突保护、审批、回滚和周/月回顾提案已通过临时文档库自动测试。Codex 项目级定期任务已按北京时间每天 09:00 启用，周一和每月 1 日在同一任务内顺序追加周/月处理；首次真实运行、长期质量、Obsidian 并发修改和一个完整日/周周期仍待人工验收，因此 P2 仍在进行中，阶段门尚未关闭。

### 目标

从增量变化的每日记录中建立可追溯检索与片段层，形成有限的候选主题和可审阅文章修改，让文章随长期积累演化而不覆盖用户编辑。

### 前置依赖

- P0 Markdown/ID 协议稳定，有足量模拟样本。
- 明确 Codex 定期任务可读的工作集边界、提案预算与失败策略。
- 用户确认文章目录、默认维护模式和回顾输出位置。

### 子任务

#### P2.0 确定性索引基线

- .NET 10 worker、CLI、配置与 migration。
- 文件 watcher 提示 + 周期扫描兜底、revision/hash、删除/移动检测。
- Markdown 解析、手工区域识别、FTS5 和结构化过滤。
- 重建命令、一致性检查、处理游标和诊断队列。

#### P2.1 片段与检索

- 先用确定性规则建立段落/列表/引用切分基线；若未来需要语义重切分，另立评测与协议版本。
- 保存 span、来源 revision、提取器版本和 supersede 链。
- 建立时间、来源、书籍、主题候选和问题检索。
- 用含中文词语、短语和中英混合内容的固定问题集比较 FTS5 `unicode61`、`trigram` 或受控 tokenizer；只有检索质量明显不足时引入 embeddings，不部署独立向量数据库。

#### P2.2 文章候选与身份

- 定义候选评分：用户意图、材料量、持续性、中心问题、跨来源价值、与现有文章重合度。
- 建立 seed → active → paused/archived 生命周期和每周期新文章预算。
- 用户指定专题优先；自动发现先产生建议，不直接大量建文件。
- 建立相似文章合并建议和重复创建阻断。

#### P2.3 提案与冲突保护

- 文章 frontmatter/revision、来源引用和锁定区域。
- 结构化写作计划、最小范围补丁、引用校验与风险分级。
- 基线 hash 检查、外部编辑识别、conflict/rebase/reject/apply 流程。
- 原子应用、变更审计、回滚和可选 Git 辅助。
- 默认正文变更全部进入审阅；低风险自动应用经过实际信任验证后再开启。

#### P2.4 调度、回顾与质量

- 每日/每周/月度/主动 workset、独占锁、提交幂等与稳定错误。
- Codex 项目定期任务需用户确认时间后创建；PKWS 不安装 Windows Task Scheduler 任务。
- 每日只处理新增变化；每周发现跨日关联；每月做长期结构建议，不默认全篇重写。
- 建立离线评测集：来源忠实、引用覆盖、重复率、冲突保护、提案可应用性和文章可读性。
- 记录协议/分析版本、workset 输入 ID、提交 hash 和结果；不把完整正文写入普通日志。

### 交付物

- 可重建的增量索引与查询 CLI。
- 片段/来源追踪、文章候选、提案审阅与应用/回滚工具。
- 周期任务定义、恢复/隔离工具和回顾输出。
- Codex workset/submission 契约、自动任务运行指南与评测报告。
- 用户操作与故障处理文档。

### 自动化验收

- 初次扫描后不变数据再次运行不新增 fragment/proposal/article。
- 修改单条记录只使相关 revision/fragment 失效并重算，不全量处理。
- 删除 index.db 后可从模拟 Vault 重建等价的可查询状态。
- 每个生成陈述都能解析到存在的来源 revision/span；缺失来源的提案不能进入 ready。
- 人工编辑文章后，旧基线提案必定冲突且文件字节不变。
- 同一 run 崩溃、租约过期和重复调度不会重复创建文章或重复应用补丁。
- 无效 submission JSON、越界 ID、提示词注入样本、过时文章基线和部分失败进入预期可恢复状态。
- 回滚恢复前一 revision，审计链连续。

### 人工验收

- 用模拟/用户批准的非敏感样本评估检索结果和片段边界。
- 用户审阅候选文章数量、重复建议、来源跳转和提案差异。
- 至少连续运行一个日/周周期，确认没有无意义 churn。
- 用户在 Obsidian 改写文章后，系统保留其措辞并给出可理解冲突说明。
- Codex 定期任务的工作集范围、通知策略和本地文件行为符合用户选择。

### 风险与降级

- 写作质量不稳定：保持“检索 + 候选材料包”，暂停自动文章草稿。
- Embedding 费用/隐私不合适：仅使用 FTS5、时间和结构化过滤。
- Codex 定期任务未运行或中断：pending 工作集保留，下次或手动重跑；原始捕获与本地检索不受影响。
- 提案冲突过多：缩小到段落/section patch，提高人工锁定和刷新基线频率。
- 文章泛滥：降低自动候选预算，只允许用户主动创建文章。

### 独立可用性

P2 依赖 P0 数据。完成 P2.0/P2.1 后，增量检索可独立使用；完整文章维护需要 P2.2–P2.4 和人工验收。

## 5. P3：科学化工具对接

### 目标

从记录与文章中生成带认识论状态、来源和不确定性的待审核候选，通过实际兼容的交换层送入科学化工具；绝不自动升级为事实。

### 前置依赖

- P2 来源 revision、片段、文章 revision、提案/审核机制稳定。
- 获得科学化工具仓库的只读检查权限并确认真实对象模型、API、认证和审核流。
- 双方对对象身份、来源、状态和删除/修订语义形成版本化契约。

### 子任务

- 审查科学化工具实际代码与数据模型，编写兼容性/差距报告。
- 对齐 Fact/Observation/Explanation/Question/Experiment/Relation/Evidence 语义；无法一一映射时保留 PKWS 候选类型，不强行转换。
- 定义 versioned exchange package、JSON Schema、批次 manifest、校验与签名/哈希。
- 实现候选提取、认识论状态、来源链、置信提示和 dedupe key。
- 默认实现单向“导出 → 对方待审核导入 → 回执”。
- 处理重复导入、来源 revision 变化、拒绝、接受、supersede 和外部 ID 映射。
- 双向同步只在回执语义稳定后设计；冲突进入人工队列，不自动改写文章。
- 建立文学/主观随笔排除策略和用户按主题/目录 opt-in。

### 交付物

- 实际仓库审查与字段映射文档。
- KnowledgeCandidate/交换包 Schema、导出器、校验器和导入适配器（以对方支持为准）。
- 审核回执、幂等/修订/冲突测试。
- 数据边界、失败恢复和人工操作说明。

### 自动化验收

- 同一候选包重复导入只创建一个待审核对象或返回同一映射。
- 来源修改后生成 superseding candidate，不静默改写已审核对象。
- 引文、作者观点、用户猜测和模型推断不会标为已证实事实。
- 缺少来源、Schema 不兼容、对方拒绝和网络/进程失败可恢复且不丢状态。
- 往返回执保持 PKWS ID、外部 ID、revision 和审核状态一致。
- 被排除的文学/主观目录不产生候选。

### 人工验收

- 用户与科学化工具实际维护者核对字段语义和审核体验。
- 抽样检查候选分类、来源、引用边界和不确定性措辞。
- 确认拒绝/修订/来源删除时两边展示不会误导。
- 若启用任何反馈到文章的流程，逐项审阅并确认不会自动改变文章结论。

### 风险与降级

- 对方无稳定 API：使用带 manifest 的 JSONL/JSON 文件交换。
- 对象语义不一致：导出通用 candidate + provenance，映射留给审核界面。
- 双向冲突复杂：长期维持单向导出 + 回执，不做自动反向更新。
- 模型分类不可靠：只输出“待分类候选”或限制为用户主动触发。

### 独立可用性

不能脱离 P2 来源体系独立使用。完成单向待审核导出即可构成 P3 的最低可用范围；双向同步不是 P3 MVP 的完成条件。

## 6. 阶段状态更新模板

每次阶段交付在 `docs/PROJECT_STATUS.md` 记录：

- 当前阶段与完成比例（按验收项，不按主观估计）。
- 已完成并验证的能力。
- 实际运行的测试命令与结果摘要。
- 未完成、失败、跳过和待人工验收项。
- 依赖/Schema/ADR 变化。
- 已知风险、回滚方式和下一步。
- 明确写出“未获授权，不启动下一阶段”。
