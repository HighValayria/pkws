# 架构决策记录

本文件记录会影响长期边界、数据安全或迁移成本的决定。状态含义：

- **Accepted**：规划基线，实施若改变必须更新本文件。
- **Proposed / Validate in P0/Pn**：推荐方向，需在指定阶段用证据确认。
- **Deferred**：刻意不在当前阶段决定。
- **User confirmation required**：需要用户选择后才能落实。

## ADR-001：Markdown 是用户内容载体，SQLite 是操作与派生状态

- 日期：2026-10-21
- 状态：Accepted
- 决定：每日原始记录和文章以普通 Markdown 长期保存；SQLite 保存幂等账本、revision、索引、任务和审计。索引可由 Markdown 重建，捕获账本因承担恢复责任而不可随索引一起删除。
- 理由：保证脱离 PKWS 仍可使用，又获得事务、增量和查询能力。
- 后果：必须处理 Markdown 与账本的跨资源恢复；不能宣称二者具备单事务原子性。
- 否决方案：只用数据库会削弱可移植性；只用 Markdown 难以可靠实现幂等、租约和高效索引。

## ADR-002：Capture Host 是原始记录的唯一自动写入者

- 日期：2026-10-21
- 状态：Accepted
- 决定：桌面 UI、Chrome 扩展和 Agent 都通过统一捕获应用层写入，Chrome 不直接访问文件；Agent 对 `Daily` 只读。
- 理由：把路径、时间、幂等、并发和恢复规则集中到一个边界。
- 后果：Capture Host 不可用时扩展只能排队；需提供清晰健康状态和恢复。
- 否决方案：各客户端直接追加会复制规则并制造冲突。

## ADR-003：桌面抽屉不做第二个完整 Markdown 编辑器

- 日期：2026-10-21
- 状态：Accepted for P0
- 决定：P0 将历史记录和当前输入连续排版，但只允许编辑当前待提交块；历史块不做整页原地编辑。外部 Markdown 编辑器可选。
- 理由：视觉上保持一张笔记，同时避免以整页保存覆盖外部修改，继续维护单一追加者边界。
- 后果：大段历史修改需打开 `doc` 中的 Markdown；未来只有在乐观并发和冲突 UX 经验证后才增加内嵌全文编辑。

## ADR-004：使用幂等账本和补偿恢复实现可靠捕获

- 日期：2026-10-21
- 状态：Accepted
- 决定：客户端生成 `request_id`；服务先记录请求状态，再追加/flush/回读 Markdown，最后提交账本。启动恢复以 `entry_id` 扫描确认结果。
- 理由：SQLite 与文件系统不存在可移植的共同事务，必须显式承认崩溃窗口。
- 后果：状态机和故障注入是 P0 核心，不可推迟到“以后加固”；账本保留提交时正文，需按敏感数据保护。
- 否决方案：直接 append 后返回无法区分“已写但响应丢失”，会在重试时重复。

## ADR-005：记录身份采用稳定 ID 与低干扰 HTML 注释边界

- 日期：2026-10-21
- 状态：Accepted — P0 已冻结 v1
- 决定：采用 .NET UUIDv7；记录块用含版本、ID、UTC 时间、时区、来源、正文 SHA-256 与字节数的 HTML 注释包围；可读正文不依赖解析器。
- 理由：支持用户编辑后的稳定映射、去重和来源跳转，且不在阅读视图展示大量元数据。
- 验证门：复杂 Markdown、损坏标记、Obsidian 编辑、行尾、Unicode 和手工复制 fixture 全部通过；UUID 库维护质量可接受。
- 降级：若块标记过于脆弱，保留开头单标记 + parser recovery，或按每条独立文件再由 daily 汇总；后者改变产品体验，需用户确认。

## ADR-006：Capture Host 从 Tauri 降级为 .NET 10 WPF

- 日期：2026-10-21
- 状态：Accepted in P0
- 决定：P0 使用 .NET 10 LTS WPF + ASP.NET Core + Microsoft.Data.Sqlite。Tauri/Rust 不再是已实现主线。
- 理由：目标机缺少 MSVC Build Tools；官方安装器因系统盘空间不足以 `0x80070070` 失败，无法形成可重复构建。既有 ADR 明确允许此时切换 WPF。开发日期接近 .NET 8 支持结束，故选择仍处 LTS 的 .NET 10。
- 证据：Debug/Release 零警告编译，核心/API 自动化测试通过，framework-dependent `win-x64` 发布通过；右缘感应、IME、多屏/DPI、睡眠恢复仍列入人工验收。
- 后果：P0 为 Windows/C# 栈；P1 继续通过版本化 HTTP/JSON 契约解耦，P2 仍可使用 Python worker。

## ADR-007：回环 HTTP 是 Chrome 扩展的默认桥接

- 日期：2026-10-21
- 状态：Accepted；P1 配对已实现
- 决定：API 仅绑定 `127.0.0.1`。桌面主令牌保持私有；用户在桌面端生成 6 位一次性码，Chrome 扩展以自身 ID 和精确 Origin 换取独立 256-bit 凭证。主机只保存扩展 ID 与凭证哈希，同一扩展重新配对即轮换旧凭证；客户端不能提交请求地址或文件路径。
- 理由：比 Native Messaging 安装简单，且允许桌面与未来本地客户端共享协议。
- 后果：普通网页即使能探测 localhost，也必须同时通过一次性码/令牌和扩展 Origin 校验；CORS 不作为认证。当前无独立服务端撤销 UI，扩展本地可忘记凭证，服务端旧凭证在同扩展重新配对时失效；通用捕获速率限制仍需后续加固。
- 降级：安全策略或 Chrome 限制不允许时切换 Native Messaging，Capture 应用层保持不变。

## ADR-008：时间由服务端确权，事件时间独立保存

- 日期：2026-10-21
- 状态：Accepted
- 决定：保存 UTC `created_at`、IANA `timezone`、由主机计算的 `local_date`；可选 `occurred_at` 表示用户声明的事件时间。默认文件归属取服务端捕获时刻。
- 理由：避免客户端时钟/伪造路径造成不一致，同时能表达补记历史事件。
- 后果：跨午夜草稿必须提示；时区变更只影响未来捕获，不重排旧文件。

## ADR-009：FTS5 先行，向量检索需用评测证明价值

- 日期：2026-10-21
- 状态：Accepted for P2 baseline
- 决定：先实现 SQLite FTS5 + 时间/来源/主题过滤；针对中文必须以固定问题集比较内置 `unicode61`、`trigram` 或受控 tokenizer。只有基线显示明显召回不足时才加入 embedding provider，初期不部署独立向量数据库。
- 理由：降低隐私、成本、依赖和重建复杂度。
- 后果：早期语义同义词召回可能有限，但基线可量化，后续增强有比较对象。

## ADR-010：文章正文更新默认生成变更提案

- 日期：2026-10-21
- 状态：Accepted
- 决定：正文变更绑定 `base_revision` 并生成最小范围 patch；应用前 hash 不一致即冲突。高影响修改必须人工批准；低风险自动应用只有用户显式启用后开放。
- 理由：无法可靠地从最终文本猜出所有人工意图，乐观并发 + 审阅比静默合并安全。
- 后果：用户会看到待审队列；系统需要控制提案数量、合并相似提案并解释变更价值。
- 否决方案：Agent 直接覆盖整篇文章会丢失人工编辑并产生无意义 churn。

## ADR-011：文章先经过候选生命周期并受创建预算约束

- 日期：2026-10-21
- 状态：Accepted as product policy
- 决定：材料先进入 fragment/candidate，满足用户意图、材料量、持续性、中心问题和独特性等信号后才建议建文；与现有文章重合时优先融合。
- 理由：产品目标是少量可读成果，不是主题文件数量。
- 后果：部分材料会长期停留为片段，这是允许的；阈值需要 P2 以真实使用反馈调整。

## ADR-012：周期任务使用短时 worker + Windows Task Scheduler

- 日期：2026-10-21
- 状态：Superseded by ADR-023
- 决定：Task Scheduler 只唤起 CLI；P2 v1 在 `agent.db` 保存 ProcessingRun，并用独占 `agent.lock` 防止并发。周/月计划每天做一次轻量 due 检查，本周期已有成功记录就退出，以便关机错过后补跑。细粒度 WorkItem/隔离队列暂未实现。
- 理由：避免自研守护调度，同时使任务失败可观察、可手工重跑。
- 后果：睡眠错过任务、重复触发和凭据环境需要集成测试；任务安装/移除由用户显式执行。

## ADR-013：科学化工具先单向交换，不假设其 API

- 日期：2026-10-21
- 状态：Accepted for planning; implementation deferred to P3
- 决定：P3 开始先检查对方真实仓库；MVP 是版本化候选包、显式待审核导入和回执。候选不等于事实，双向同步不是 MVP 必需。
- 理由：当前没有对方实际 Schema/API，提前设计双向写入会制造错误耦合。
- 后果：早期认识修订不会自动回流文章；可以用人工回顾处理。

## ADR-014：Git 是可选第二道版本保护，不是事务机制

- 日期：2026-10-21
- 状态：User confirmation required
- 决定建议：项目源代码应初始化本地 Git；真实 Vault 是否启用 Git 另行选择。自动提交只在明确授权后实现，且不包含运行数据库、日志和密钥。
- 理由：Git 适合审阅和恢复文本历史，但不能解决并发写入或幂等。
- 待确认：当前空目录是否初始化 Git；未来 Vault 大小、既有同步方式和用户的提交偏好。

## ADR-015：LLM 提供方与数据策略延后到 P2 前确认

- 日期：2026-10-21
- 状态：Superseded by ADR-023
- 原决定：建立 OpenAI 风格提供方抽象并由用户显式配置密钥。用户后续明确不采用任何 API，该实现已移除。
- 理由：P0/P1 不需要 LLM，当前选择会过早绑定隐私、费用与能力。
- 后果：不再需要提供方、密钥、费用或 HTTP 重试配置；数据是否被 Codex 任务读取由用户对该项目任务的授权范围决定。

## 未决但不阻塞当前规划

- P0 不再注册或配置全局键盘组合；从屏幕右缘感应按钮或再次启动程序唤起。
- `doc` 内后续 `Writing`、wiki 与 Agent 产物的具体子目录结构。
- 是否在 Vault 中保存人类可见的完整 proposal 文件，还是只保存 review 摘要、完整补丁放本机状态。
- P2 评测后是否启用 embeddings 与低风险自动应用。
- 科学化工具的实际接口、对象约束和回执语义。

## 官方能力核对（2026-10-21）

- [Chrome Side Panel API](https://developer.chrome.com/docs/extensions/reference/api/sidePanel) 确认为 Chrome 114+、Manifest V3，并说明物理左右位置可由用户设置；因此不把“强制右侧”作为扩展能力承诺。
- [SQLite FTS5](https://www.sqlite.org/fts5.html) 确认 FTS5 与内置 tokenizer/`trigram` 能力；中文效果仍需用项目语料评测，官方存在能力不等于检索质量已经验证。

## ADR-016：桌面唤起不使用全局键盘组合

- 日期：2026-10-22
- 状态：Superseded by ADR-017（“不使用全局键盘组合”的部分仍有效）
- 背景：先后选择的键盘组合与 OneNote 发生直接冲突，并在验证另一组合后出现了 Clash Verge/系统代理异常。Windows `RegisterHotKey` 的成功只表示该组合未被同一注册机制占用，不能排除低级键盘钩子、输入法或应用内快捷键。
- 决定：删除快捷键配置字段、设置界面和 Win32 注册代码。最初以托盘和重复启动作为替代入口；随后入口方案由 ADR-017 重构为屏幕右缘感应按钮。
- 理由：不再捕获系统级键盘输入，从机制上消除与代理工具、输入法和其他软件的键盘竞争，同时保持一到两次点击即可记录。
- 后果：纯键盘全局唤起不再提供。旧 `config.json` 中的 `hotkey` 字段由反序列化器忽略，下次保存时自然移除。
- 替代方案：为某个组合做占用探测不足以覆盖键盘钩子；自动创建任务栏固定项属于系统级修改且兼容性差。

## ADR-017：右缘感应入口、连续笔记界面与固定 doc 根

- 日期：2026-10-22
- 状态：Accepted
- 背景：托盘入口不够直接，原界面把 Vault、时区、路径模板、API 和“已有内容（只读）/新增内容”暴露为主要产品概念，偏离随手记工具。用户要求像一张笔记，并提出鼠标贴到屏幕右缘后出现按钮的唤起方式。
- 决定：使用独立透明 WPF 感应窗占据当前屏幕右缘中部 6 像素；悬停时展开按钮，点击后隐藏感应窗并显示右侧笔记面板。面板收起后恢复感应窗。不注册全局快捷键、不使用托盘、不写注册表。历史记录与当前 Markdown 输入连续排版，每段可见元信息仅为 `HH:00`；历史块按 Markdown 渲染，输入块提供常用格式操作和纯本地预览，任何内容均不执行。用户文档根固定为 `<程序目录>/doc`，设置仅保留路径查看、打开文件夹和退出。
- 理由：贴边动作低摩擦且不与键盘、输入法或代理软件竞争；连续页面符合笔记心智；固定 doc 根为后续 Agent/wiki 留出稳定边界并去除首次配置负担。
- 后果：应用必须常驻才有贴边入口；透明顶层感应窗、多显示器、DPI、任务栏位置、全屏遮挡和误触需人工验收。若程序安装在不可写目录，启动自检会明确失败，因此当前仍按便携目录交付。历史块视觉上与输入一致，但为维护单一追加者和避免覆盖，P0 不提供历史全文原地编辑。旧 Vault 路径中的数据不自动移动或删除；若用户需要迁移，必须先备份并另做显式迁移流程。
- 替代方案：托盘已被用户否决；全局快捷键因冲突风险禁用；整页可编辑会引入与外部修改的并发覆盖，P0 不采用。

## ADR-018：P1 草稿冻结来源，微信读书可读格式由 Capture Host 生成

- 日期：2026-10-22
- 状态：Accepted in P1
- 背景：Side Panel 会跨章节和标签页持续存在。如果提交时才读取当前 DOM，已写一半的草稿可能被静默绑定到另一书或章节；如果由扩展直接拼最终 Markdown，格式和安全规则会与桌面单一写入者分叉。
- 决定：草稿首次出现评论时冻结 `SourceContext`；当前页面状态独立更新，来源差异只提示，不覆盖草稿。用户可按冻结来源保存，或显式改绑；改绑同时生成新的 `request_id`。扩展提交结构化评论和来源，Capture Host 验证后统一组合为“来源 / 我的笔记”Markdown，再进入 P0 账本与追加链路；协议仍兼容其他客户端提交可选引用。
- 理由：来源绑定可在客户端交互层被用户看见和控制，而最终 Markdown 规则仍只有一个可信实现；幂等 payload 继续覆盖原始结构化请求。
- 后果：扩展必须持久化草稿与稳定请求 ID，并把当前上下文和草稿上下文分开。服务端可读正文不再等于 `CaptureRequest.content` 的逐字副本，但账本仍保存原始评论和完整 `SourceContext`。
- 替代方案：保存时动态读取页面会产生错源；扩展预拼 Markdown 会复制序列化规则；每本书单独写文件会破坏统一每日原始记录模型。

## ADR-019：P1 暂停网页选文引用，收窄为来源绑定的 Markdown 笔记

- 日期：2026-10-22
- 状态：Accepted for P1 v0.1.2；选文能力 Deferred
- 背景：按钮读取和右键菜单方案在真实微信读书阅读页上均未能稳定取得用户选区，且扩展 v0.1.1 的实际人工验证仍失败。用户明确决定跳过该功能，继续验收其余笔记闭环。
- 决定：从 Chrome 扩展移除引用按钮、引用预览、右键菜单、选区缓存与读取代码，并撤销 `contextMenus`、`scripting` 权限及 frame 注入范围。当前 P1 只识别来源、输入 Markdown、冻结来源并安全保存。Capture API 与 `SourceContext` 中现有的可选选文字段暂不做破坏性删除，以兼容既有记录和客户端。
- 理由：不可用入口会误导用户，额外权限也不应为未交付能力保留。保留协议兼容字段比立即发布破坏性契约版本更安全。
- 后果：网页选文不再是 P1 v0.1.2 的验收项；用户仍可把需要的文字手工粘贴为普通 Markdown。扩展最低兼容基线回到 Side Panel API 所需的 Chrome 114。若将来重启该能力，必须由用户另行授权范围，并先建立真实页面可复现测试与明确的浏览器权限方案。

## ADR-020：P2 Worker 沿用 .NET 10 模块化单体

- 日期：2026-10-22
- 状态：Accepted in P2
- 背景：路线最初建议 Python worker，但 P0 已有稳定的 C# Markdown 序列化、哈希、SQLite 和 Windows 发布链。再引入 Python 会增加一个运行时、跨语言契约和计划任务部署面。
- 决定：新增 `Pkws.Agent` 无 UI 核心库和 `pkws-agent` 短时 CLI，保持与桌面进程分离但复用 .NET 10 和 `Pkws.Core`。不引入多 Agent 框架。
- 理由：减少依赖与部署复杂度，同时保留版本化 workset/submission、索引和文章策略边界。
- 后果：文本评测生态不如 Python 丰富；若未来确有离线 embedding 或科学计算需求，应通过版本化边界增加专用工具，而不是让其接管原始写入。
- 替代方案：Python 3.12 worker 能快速使用模型生态，但对当前 P2 纵向闭环没有足够收益。

## ADR-021：P2 控制账本与 FTS 派生索引物理分离

- 日期：2026-10-22
- 状态：Accepted in P2
- 背景：提案、文章 revision 和运行审计不能因重建全文索引而丢失；单个 `agent.db` 无法明确满足“删除索引可重建”的操作语义。
- 决定：`agent.db` 保存来源 revision、fragment、主题、文章版本、提案和运行账本；`index.db` 只保存 FTS5 表。每次打开会检查活跃 fragment 数量与 FTS 数量，不一致时重建派生索引。
- 理由：用户可安全删除 `index.db`，而审批和版本历史继续存在；无需为小型本地应用引入独立数据库服务。
- 后果：跨两个 SQLite 文件的索引更新不是不可分割的长期事实事务，但 index 是派生数据，启动一致性检查可恢复。`agent.db` 必须备份，不能声称可从 Markdown 完整恢复。
- 替代方案：所有表放一个 DB 更简单，但容易误删控制状态；把控制状态写入 Vault 会污染阅读体验并增加外部编辑冲突。

## ADR-022：所有 P2 正文变化默认人工批准并使用结果哈希恢复

- 日期：2026-10-22
- 状态：Accepted in P2
- 背景：真实模型质量尚未在用户语料上建立信任，低风险自动应用也可能产生无意义 churn。文件写入与 SQLite 账本之间仍存在崩溃窗口。
- 决定：文章、周回顾和月回顾全部先保存 `pending` 提案。Codex 提交的修订只能给出当前文章中唯一匹配的精确 `find/replace`；受保护 frontmatter、来源区和 `pkws:locked` 区域不可修改。批准后执行原子替换和回读；若重试时文件 hash 已等于提案结果，则只补交账本。
- 理由：把模型判断与文件副作用分开，优先保护用户人工编辑，并让崩溃恢复幂等。
- 后果：日常使用多一步审核；只有后续真实长期验收证明某类操作可靠，才考虑显式启用 `auto_low_risk`。
- 替代方案：直接自动写入更省操作，但在未验证阶段无法接受；整篇重写更易生成，但会扩大冲突和措辞丢失风险。

## ADR-023：Codex 定期任务是 P2 的调度与推理层

- 日期：2026-10-22
- 状态：Accepted in P2
- 背景：用户不打算配置或付费调用独立模型 API，而是希望利用 Codex 的项目定期任务完成整理。本地工具仍必须在会话之外保持幂等、冲突保护和审批状态。
- 决定：移除 OpenAI 兼容 HTTP 客户端、API Key/模型配置和 Windows Task Scheduler 脚本。`pkws-agent prepare` 导出有界 `CodexWorkset v1`，Codex 生成 `CodexSubmission v1`，`submit` 校验封闭 ID 集合、文章基线、周期类型和预算后只保存 pending 提案。日/周/月时刻待用户指定后，使用 Codex 项目级自动任务创建。
- 理由：不需要用户管理模型密钥或两套模型费用，同时使“推理”与“可恢复文件副作用”保持强边界。
- 后果：本地文件任务需电脑开机且 Codex 桌面应用可用；定期任务的实际执行和长期质量仍须人工验收。即使 Codex 任务被中断，pending 工作集和提案仍留在 `agent.db`。
- 替代方案：Windows Task Scheduler 只能解决唤起，不能提供语义推理；内置 API 客户端与用户明确意图冲突；直接让 Codex 写 Daily/文章会绕过数据安全协议。
